## 监控

一个功能是否需要考虑高性能，需要基于场景以及监控指标来考虑，
因为引入高性能，很有可能会增加设计/架构的复杂度，所以需要避免过度设计。

从几个维度去评估一个功能的设计：

- 访问量
- 一致性
- 实时性

评估高性能的监控指标：

- 常规的系统监控，这包括CPU使用率、系统负载、内存使用率、网络I/O、磁盘I/O、磁盘使用率等
- 应用层服务的监控
  - 吞吐率（Throughput）
  - 请求处理时间
  - 请求 I/O 等待时间，尤其是涉及系统调用的 I/O 等待时间。
  - 数据库/缓存的监控
- 用户测服务质量的监控，包括响应时间

### 吞吐率（Throughput）

吞吐率（Throughput）是指单位时间内的请求数，单位是 `reqs/s`。它是指在一定并发用户数的情况下，**服务器处理请求能力**的量化体现。通过

一般通过简化模型，对特定的有代表性的请求进行**压力测试**，然后根据需要，对多个请求的吞吐率按照比例计算**加权平均值**，从而得到服务器的最大吞吐率，了解服务器的承载能力，并且结合用户规模考虑适当的扩展方案。

计算吞吐率的压力测试的准备条件：

- 并发用户数
- 总请求数
- 特定的请求

并发策略的设计就是在服务器同时处理较多请求的时候，如何合理协调并充分利用CPU计算和I/O操作，使其在较大并发用户数的情况下提供较高的吞吐率。

希望服务器支持较大的并发数，那么就要尽量减少上下文切换次数

## 单体服务的演进

单体服务指**所有业务都在一起**的服务，一般所有服务都始于单体服务。

### I/O 性能优化

I/O 性能的瓶颈往往在以下几种 I/O，因为它们的访问速度相对 CPU /内存来说要慢很多:

- 网络 I/O
- 磁盘 I/O

这些I/O操作需要由内核**系统调用**来完成，同时系统调用需要 CPU 来调度，
而 CPU 的速度是非常快的，这就使得 CPU 不得不浪费宝贵的时间来等待慢速 I/O 操作。

所以希望能够让 CPU 花费足够少的时间在 I/O 操作的调度上，这样就可以腾出更多的 CPU 时间来完成更多的 I/O 操作，让高速的 CPU 和慢速的 I/O 设备更好地协调工作。

慢速 I/O 设备和内存之间的数据传输方式目前主要通过 DMA（直接内存访问，Direct Memory Access），它可以不经过 CPU 而直接进行磁盘和内存的数据交换。在DMA模式下，CPU 只需要向**DMA控制器**下达指令，让DMA控制器来处理数据的传送即可，DMA控制器通过**系统总线**来传输数据，传送完毕再通知CPU，即**减少了 CPU 的等待时间**，也就腾出了更多的 CPU 时间，这样就在很大程度上降低了CPU占用率，大大节省了系统资源。而它的传输速度主要取决于慢速设备的速度，所以并**不会减少数据传输的时间**。

##### 持久连接

持久连接（Keep-Alive）也称为**长连接**，它本身是TCP通信的一种普通方式，即在一次TCP连接中持续发送多份数据而不断开连接，与它相反的方式称为短连接，也就是建立连接后发送一份数据便断开，然后再次建立连接发送下一份数据，周而复始。一般而言，是否采用持久连接，完全取决于应用的特点和需要。

持久连接的动机就是尽量减**少连接次数**，尽量重用连接通道。

从性能的角度看，建立TCP连接的操作本身便是一项不小的开销，所以在允许的情况下，连接次数越少，越有利于性能的提升。对于**密集型**的图片或网页等**小数据请求**处理有着明显的加速作用。

在长连接的情况下，总的系统调用数减少了一半左右，尤其是 socket 的 accept() 和 close() 的减少量，它们消耗的时间，比不使用长连接的时候减少了很多，这在整体时间中占有不小的比例。

## 缓存

缓存是让数据**更接近于使用者**，目的是**让访问速度更快**。
工作机制是先从缓存中读取数据，如果没有，再从慢速设备上读取实际数据并同步到缓存。

可以被缓存的数据：

- 那些经常读取/频繁访问的数据
- 热点数据
- I/O瓶颈数据
- 计算昂贵的数据
- 符合5分钟法则和局部性原理的数据

**缓存命中率**是从缓存中读取数据的次数与总读取次数的比率，命中率越高越好。
`缓存命中率 = 从缓存中读取次数/〔总读取次数（从缓存中读取次数 + 从慢速设备上读取次数）〕`。
这是一个非常重要的监控指标。

缓存回收策略基于几个维度考虑：

- 空间/容量，指缓存占用的空间或者数量达到上限时采用的回收策略
  - FIFO
  - **LRU**（Least Recently Used），实际应用中采用的比较多
  - LFU（Least Frequently Used）
- 时间，指缓存的**存活期（TTL, Time To Live）**到期后或者是空闲期（TTI, Time To Idle）多久后采用的回收策略

### 缓存数据 && 同步数据

- 如果对缓存数据一致性要求不是那么高，数据量也不是很大，则可以考虑**不过期缓存**，并**定期全量**同步缓存。
- 对于**长尾访问**（单个访问频率很低、但种类以及数量巨大）的数据、大多数数据**访问频率都很高**（热点数据）的场景，或者是缓存空间足够，都可以考虑**不过期缓存**，比如用户、分类、商品、价格、订单等。当缓存满了，可以考虑用 LRU 机制驱逐老的缓存数据。
- **热点数据**经常使用**过期缓存**，即缓存比较短的时间。这种缓存可能存在一段时间的**数据不一致**情况，需要根据场景来决定如何设置过期时间。
- 最好将数据进行**维度化**并**增量更新**（只更新变的部分）

同步策略：

- 定时更新，适合对数据一致性不高的场景
- 订阅更新，通过订阅数据更新的消息，及时对缓存数据进行更新，适合对数据实时性要求比较高的场景。

### 多级缓存设计

所谓多级缓存，是指在整个系统架构的不同系统层级进行数据缓存，以提升访问效率，这也是应用最广的方案之一。

缓存数据距离使用者的距离，从近到远：

1. 浏览器缓存
2. CDN 缓存
3. 代理/接入/网关层缓存，比如 Nginx，gateway 等
4. 应用服务级缓存
   1. 应用层本地缓存
   2. 分布式缓存

### 应用服务级缓存

#### 服务内的缓存

优点：

- 不需要序列化
- 速度最快

缺点：

- 数据量不大
- 重启后丢失

做了本地缓存，需要我们去考虑**数据一致性**，即何时失效或更新缓存。

- （推荐）如果可以**订阅数据变更**消息，那么建议订阅变更消息以进行缓存更新。
- 如果无法订阅消息或者订阅消息成本比较高，并且对短暂的数据一致性要求不严格，那么可以设置合理的过期时间，过期后再查询新的数据。

#### 服务使用的外部分布式缓存

优点：
  
- 支持更大的缓存空间，不受服务本身的内存空间限制

缺点：

- 需要序列化

#### 缓存使用模式

SoR（system-of-record） 是指业务真正操作的数据源。

缓存使用模式:

- Cache-Aside，适合**读多**的场景
  - 读场景，先从缓存获取数据，如果没有命中，则由业务代码回源到 SoR 并将源数据放入缓存。
  - 写场景，先将数据写入 SoR，写入成功后立即将数据同步写入/清空缓存。
- Cache-As-SoR 之 Write-behind 回写模式，适合**高并发**场景
  - 把 Cache 作为业务真正操作的数据源，通过**异步**将 Cache 数据同步到 SoR。
  - 异步操作可以实现批量写，合并写，延时和限流等。

最佳实践：

当DB没有数据时，写入 `NULL` 对象到缓存。读取数据时，如果发现NULL对象，则返回null，而不是回源到DB。通过这种方式可以防止当 key 对应的数据在 DB 中不存在时频繁查询 DB 的情况。

### 浏览器缓存

浏览器缓存是指当我们使用浏览器访问一些网站页面或者HTTP服务时，根据服务器端返回的缓存设置响应头将响应内容缓存到浏览器，下次可以直接使用缓存内容或者仅需要去服务器端验证内容是否过期即可。

好处是可以**减少**浏览器和服务器端之间来回**传输的数据量**，**节省带宽以提升性能**。

![HTTP Cache](http-cache.png)

#### HTTP 缓存

- Last-Modified，表示文档的最后修改时间，当去服务器验证时会用到这个时间。
- If-Modified-Since，其值是上次请求响应中的 Last-Modified，即浏览器会用这个时间去服务器端验证内容是否发生了变更。
- Expires，http/1.0 规范定义，表示文档在浏览器中的过期时间，当缓存内容时间超过这个时间，则需要重新去服务器获取最新的内容。
- Cache-Control，http/1.1规范定义，表示浏览器缓存控制，max-age=20表示文档可以在浏览器中缓存20秒。

根据规范定义 Cache-Control 优先级高于 Expires，优先使用 Cache-Control。

当刷新（按 `F5`/`Ctrl+F5`/`地址栏输入地址`）时，都会去服务器端验证内容是否发生了变更。

## 队列的应用

主要的应用场景：

- 异步处理，可以**提升主流程响应速度**，而非主流程/非重要处理可以异步处理，还可以将任务聚合进行批量处理，一般使用**消息队列/任务队列**来实现。
- 系统解耦，针对不需要实时处理、不需要强一致，只需要**保证最终一致性**即可的业务，一般使用**消息队列/任务队列**来实现。
- 数据同步
  - 全量更新，一般可以订阅**消息队列/任务队列**来实现。
  - 部分变更场景，需要保证数据修改的有序性，一般使用**数据总线队列**来实现。
- 流量削峰，将请求暂时放入队列，通过队列暂存和限流，使处理速度变平滑，从而不会因瞬间压力太大而压垮服务，一般使用**缓冲队列/请求队列**来实现。

### 消息队列 MQ

常见的订阅方式：

- 点对点，一个消息只有一个消费者
- 发布订阅（pub/sub），一个消息可以有多个消费者

推送方式：

- 拉取
- 推送

一般会在应用系统中采用**双写模式**，**在写事务成功后写 MQ**，然后**异构系统可以订阅 MQ** 进行业务处理。
因为在双写模式下没有事务保证，所以会可能出现数据不一致的情况，如果对一致性要求没那么严格，则这种模式是没问题的。

## 扩展

扩展的目的也是提高服务集群整体的吞吐量。

- 纵向扩展，即升级硬件。如果能通过硬件快速解决，而且**成本不高**，应该首先通过硬件扩容来解决问题。
- （常用）横向扩展，部署更多的**副本**。提供**统一代理入口**，通过**负载均衡机制**将请求路由到相应的副本。

如果用户会话数据保存在节点中，就需要在负载均衡器开启**会话黏滞（sticky）**特性。

针对横向扩展，一般建议将会话保存到**分布式缓存**中，这样负载均衡只需要采用**轮询/哈希策略**即可，在高并发时请求会更加平均。

如果数据库的瓶颈是读造成的，则此时可以通过**主从架构和读写分离策略**将读的流量分散到更多的从服务器上，
**写数据时写到主数据库，读数据时读取从数据库**。

随着应用部署数量的增多，**数据库连接**也会成为瓶颈，一般会通过**主从架构**提升连接数，也可以使用**数据库中间件**提升连接数。所有应用只调用中间件，由中间件访问数据库，减少整体的连接数。

### 负载均衡策略

- 会话黏滞（sticky）
- 轮询
- 哈希，一般采用一致性哈希策略

## 服务拆分

当单体服务变的很臃肿，或者一部分服务的访问频率非常高的时候，就需要考虑进行服务的拆分。
服务拆分的顺序，从小到大：

1. 基于业务拆分，这是一种垂直拆分方法，拆分后的每个系统都有明确的**业务边界**。
2. 基于读写操作进行拆分，即**读写分离**。

### 基于业务拆分

当业务膨胀到一定程度后，就需要对业务进行拆分，这样便于对指定部分对业务进行扩展，避免全量扩展造成资源浪费。

拆分时要**基于业务**进行解耦，将功能分离到不同系统上。
拆分后系统之间是物理隔离的，应用层面原来是直接进程内**方法调用**，现在需要改成 **RMI （远程方法调用）**。

伴随着业务拆分，同时也会对相关的业务数据进行拆分。

拆分后，系统之间需要使用带**服务注册/发现功能的SOA框架**来进行交互。服务化后，服务提供者可以根据当前网站状况随时扩容。通过**服务注册中心**，服务消费者不需要进行任何配置的更改，就可以发现新的服务提供者并使用它。

将`缓存/限流/防刷`从各应用系统中拆出来，放到接入层实现。

可以借助队列，来将一部分任务拆分到后台执行。

### 基于读写操作进行拆分（读写分离）

随着访问量的增加，根据读写操作的比例特征进行**读写分离**，避免因为某一种操作出现异常造成其他操作不可用。
所以需要把这些**操作拆分到不同的服务**中，从而使写出现问题时不会影响到读。

针对读服务的优化：

- 使用缓存提升性能
- 使用数据异构，将分散在多处的数据聚合到一处，以提升系统的性能和可靠性

主数据库向缓存/ ES 同步时会有一定的延迟，如果需要**强一致性的读**，那么直接**读主库**吧。
不是所有的系统都需要读主库，需要根据业务场景做出限制。

## 针对大数据量的拆分

单库单表会随着数据量增长出现**性能瓶颈**，此时就需要**分库、分表，或者分库分表**。

分库分表后的问题以及解决方案：

- **跨库join**可以考虑通过如全局表、ES搜索等**异构数据机制**来实现。
- **自增 ID 问题**可以通过**不同自增步长**或**分布式 ID 生成器**解决。
- **分布式事务**可以考虑事务表、补偿机制（执行/回滚）、TCC模式（Try-Confirm-Cancel）、Sagas模式（拆分事务+补偿机制）等，**业务应尽量设计为最终一致性，而不是强一致性**。

### 分库 && 分表

- 基于业务边界，进行垂直拆分
- 对大数据量的库和表进行水平拆分

**水平拆分算法**可以是

- 哈希取模
- 分区
- 路由表

#### 哈希取模

一般基于相关业务的**聚合根的主键**来进行分库分表，有助于保证**同一业务边界内**的事务。

优点：

- 数据分散相对比较平均

缺点：

- **非主键查询**时需要跨库/跨表查询，可以使用异构数据来解决。
- **扩容**需要建立新集群并进行全量数据迁移，解决方案：
  - 在初期规划时**冗余**足够数量的分库分表
  - 使用**一致性哈希算法（哈希环+虚拟节点）**来进行分库分表

##### 分区 && 路由表

按照时间分区、范围分区等进行分库分表。
如果分区规则很复杂，则可以有一个路由表来存储分库分表规则。

分区的缺点是存在热点，但是易于水平扩展，能避免数据迁移。

### 异构数据

数据异构主要按照**不同业务查询维度**建立表结构，针对读的场景，可以按照不同维度进行查询。
数据异构有查询维度异构、聚合数据异构等。
在数据量和访问量双高时使用数据异构是非常有效的，但增加了架构的复杂度。

异构数据的**同步**一般通过**订阅 MQ** 来实现。

查询维度的异构数据主要存储数据之间的关系，然后通过查询源库查询实际数据。
但有时可以通过**数据冗余**存储来**减少源库查询量**来提升查询性能。

聚合数据异构时把数据聚合后异构存储到 KV 存储集群（如存储JSON），
这样只需要**一次查询**就能得到所有的展示数据。这种方式一般是要系统有了一定的数据量和访问量时再考虑。

### 自增 ID

一般推荐采用**分布式 ID 生成器**，例如 Snowflake 雪花算法。

### 分布式事务

在一般场景中，只要保证单库事务能工作即可，跨库通过一些机制**保证最终一致性**即可，**在高并发高可用的场景下不应该采用强一致模型**。
