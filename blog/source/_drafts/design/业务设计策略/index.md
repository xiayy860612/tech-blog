## 时间设计

- DB，UTC
- Entity，UTC 时间，比如 Java Instant，Python datetime
- DTO，使用 ISO 8601 进行序列化
- 后端，统一使用 UTC 时间进行计算和查询
- 前端，根据用户时区进行展示，传递时间范围类型或者绝对时间的左闭右开区间

## 幂等

幂等指同一个操作无论执行多少次，**产生的结果都是一样的**。
尤其是一些在可以**重试**的场景下，保证业务数据不会出错。
读操作天然幂等，所以幂等操作主要针对新增和修改操作。

实现幂等的核心思想通常是：一锁、二判、三更新。

实现方式：

- 唯一索引，适用于**插入操作**，重复请求会抛出 DuplicateKey 相关异常。
- (优先)乐观锁，适用于**更新操作**，通过比较预期的**更新时间戳/版本号**来更新，更新成功则可以执行操作；更新失败则为重复请求。
- (优先)状态机，适用于**更新操作**，通过比较预期状态来更新最新的状态。
- 悲观锁，适用于并发不高，强一致性要求高的场景，例如 `select ... for update`

| 方案 | 核心手段 | 适用场景 | 复杂度 | 性能 |
| :--- | :--- | :--- | :--- | :--- |
| **数据库唯一索引** | Unique Key | 插入防重（注册/发帖） | ⭐ | ⭐⭐⭐⭐ |
| **乐观锁** | 时间戳/Version 字段 | 更新金额、库存（读多写少） | ⭐⭐ | ⭐⭐⭐⭐ |
| **状态机** | Where status=... | 订单状态流转 | ⭐ | ⭐⭐⭐⭐⭐ |
| **悲观锁** | Select for Update | **强一致性、高冲突、防超卖** | **⭐⭐** | **⭐⭐** |

## 防重

防重是为了**拦截**重复的请求进入核心业务逻辑。
那对数据库的影响自然就只有一次，也就达成了幂等的效果。

一般可以通过 **Token 机制**来实现，**防止前端重复提交**，通常结合 Redis 使用；
当前端提交时会带上 token，去 redis 检查 token 是否存在，存在则删除 token 然后执行操作；不存在则为重复请求。
